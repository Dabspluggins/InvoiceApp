Auth Flows

1
User fills login form — /auth/login: email, password, Cloudflare Turnstile CAPTCHA
↓
2
Middleware rate check — 4 POST attempts per 15min per IP (in-memory Map, resets on cold start)
↓
3
POST /api/auth/login — validates body (email, password, captchaToken required)
↓
4
Upstash rate check — loginLimiter.limit(ip): 5 attempts per 15min per IP. Returns 429 with retryAfter on block.
↓
5
supabase.auth.signInWithPassword() — server-side with captchaToken. On failure: always returns "Invalid email or password." (no provider message leakage)
↓
6
MFA check — supabase.auth.mfa.getAuthenticatorAssuranceLevel(). If nextLevel = aal2 and currentLevel ≠ aal2, returns { mfaRequired: true }
↓
7a
No MFA — POST /api/sessions/register → trust token stored. Redirect to /dashboard.
7b
MFA required — Browser shows TOTP screen. User enters 6-digit code. supabase.auth.mfa.challengeAndVerify() from browser client. On success → /dashboard.
1
User fills signup form — /auth/signup: email, password (12+ chars), Turnstile CAPTCHA
↓
2
Client validation — passwords match, length ≥ 12
↓
3
POST /api/auth/signup — validates body; enforces 12-char rule server-side too
↓
4
Upstash rate check — signupLimiter.limit(ip): 3 accounts per hour per IP
↓
5
supabase.auth.signUp() — server-side. emailRedirectTo = NEXT_PUBLIC_SITE_URL/auth/callback
↓
6
Supabase sends confirmation email — user clicks link → /auth/callback
↓
7
/auth/callback — exchanges token for session. Session cookie set. Redirect to /dashboard.
1
User clicks "Continue with Google" — browser calls supabase.auth.signInWithOAuth({ provider: 'google' })
↓
2
Redirect to Google — user authenticates with Google
↓
3
Callback to /auth/callback — Supabase exchanges authorization code for session
↓
4
Session cookie set — redirect to /dashboard
①
Every request — middleware calls supabase.auth.getUser() which auto-refreshes the session cookie when the access token nears expiry
②
Every 30 seconds — SessionHeartbeat component POSTs to /api/sessions/heartbeat → updates user_sessions.last_active
③
Idle timeout — IdleTimer monitors inactivity. If idle_timeout_minutes set in profile, auto-logs out and redirects to /auth/login
④
Trusted devices — trust_token stored (30-day expiry). On next login from same device, token submitted to /api/sessions/trust-device-token → skips MFA
⑤
Revocation — User can revoke specific sessions (/settings/revoke-sessions) or all sessions (/api/settings/revoke-sessions)

Key Data Flows

1
Create invoice — /invoice page: user fills business info, client details, line items, due date
2
Save as draft — POST/PATCH to database: invoices + line_items tables. Status = 'draft'.
3
User clicks Send — modal: recipient email, subject, custom message
4
POST /api/send-invoice — rate checked (50/hour/user). Generates unique share_token.
5
Resend email dispatch — HTML email with invoice details, payment info, "View Invoice" → /i/[share_token]
6
Status → 'sent' — logAudit('invoice.sent') recorded. share_token stored in invoices table.
7
Client opens /i/[share_token] — record_invoice_view() RPC increments view_count, sets viewed_at
8
Client downloads PDF — html2pdf.js generates PDF entirely in browser. No server involvement.
1
Client created — system generates portal_token: 16 random bytes, hex-encoded (crypto.randomBytes)
2
Token stored — clients.portal_token + portal_token_expires_at = now + portal_validity_days
3
User shares link — /portal/[portal_token] sent to client
4
Client visits portal — server validates token against clients table using service_role (bypasses RLS)
5
Invoice list rendered — all invoices for that client, grouped by currency, with status badges (PAID / OVERDUE / PENDING)
6
No auth required — purely token-gated. Token can be regenerated at any time from /clients page.
1
Create estimate — /estimates/new: title, line items with optional min_price, negotiation settings, valid_until
2
Status: 'draft' — saved with unique client_token
3
POST /api/estimates/[id]/send — Resend emails client with /estimates/[id]/review?token=[client_token] link
4
Status: 'sent' — estimate_events record: { event_type: 'sent', actor: 'owner' }
5a
Client approves — POST /api/estimates/[id]/client-action { action: 'approve' }. Status → 'approved'.
5b
Client revises — client proposes new prices or removes items. Status → 'revised'. Owner sees changes.
6
Owner accepts/rejects negotiation — accept updates line items, estimate re-sent. Reject returns to previous state.
7
Convert to invoice — POST /api/estimates/[id]/convert creates new invoice from estimate data. Status → 'converted'.

Security

🔒 HTTP Security Headers

  • X-Content-Type-Options: nosniff
  • X-Frame-Options: SAMEORIGIN
  • Referrer-Policy: strict-origin-when-cross-origin
  • Strict-Transport-Security: 2 years + preload
  • Permissions-Policy: camera, mic, geolocation blocked
  • Content-Security-Policy-Report-Only (Phase 1)

🚦 Rate Limiting

  • Login: 4/15min/IP (middleware) + 5/15min/IP (Upstash)
  • Signup: 3/hour/IP (Upstash)
  • Send invoice: 50/hour/user
  • Contact form: 5/hour/IP
  • Backup codes: 5/15min/user
  • Admin announcements: 10/24h/user

🔑 Authentication & MFA

  • TOTP MFA via Supabase Auth (AAL2 step-up)
  • Backup codes hashed via crypto.randomBytes()
  • Trusted device tokens (30-day, hash-stored)
  • Configurable idle timeout per user
  • Session revocation (single or all)
  • Google OAuth support

🗃️ Data Security

  • RLS on all 20 tables — users see only their rows
  • audit_logs: service_role insert only (un-forgeable)
  • user_sessions: service_role write only
  • Admin tables: revoked from anon + authenticated
  • logError() strips PII before Sentry — requestId only
  • Auth errors always return generic message

🔐 Password & Input

  • Minimum 12 characters enforced client + server
  • Cloudflare Turnstile CAPTCHA on login + signup
  • captchaToken passed server-side to Supabase
  • escHtml() for all user content in emails
  • Body validation on all API routes

📡 CSP (Phase 1 — Report Only)

  • Violations reported to Sentry — nothing blocked yet
  • Known violations: wasm-eval (Next.js/Turbopack)
  • Known violations: vercel.live (preview only)
  • Phase 2: add wasm-eval + vercel.live (preview), enforce
  • Extended report period due to low user count
